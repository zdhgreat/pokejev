# 工作原理

[English](../how-it-works.md) · [README](../../README.zh-CN.md)

## 一个回合的流程

1. **poke-env** 从 Showdown 服务器收到对战请求，即当前合法的招式和换人。
2. **`facts.py`** 为每个选项计算以下事实：

   | 选项 | 事实 |
   |---|---|
   | **招式** | 预估伤害（占对手 HP 的百分比）、是否可能击倒、属性克制、命中率、先制度、反伤、降自身能力、异常状态、强化、回复、场地陷阱、连续使用次数 |
   | **太晶化选项**（v1 起） | 同一招式太晶化后的版本，伤害按新的本系加成调整，并标出变成的属性 |
   | **换人** | 后备宝可梦的 HP、对位分数、是否更快 |
   | **下一回合**（v2 起） | 对手的最佳回击（已暴露的招式，否则按本系属性估算）及其对我方或换上的宝可梦造成的伤害；谁先出手；双方是否会被击倒 |

   - **伤害**来自 **poke-env 的 Showdown 计算器**，对手能力值为估算值；计算器无法运行时，使用我们自己的估算。自己的估算也覆盖了威力可变的招式（重磅冲撞、踢倒、陀螺球、愤怒门牙、扑击、欺诈、喷火、辅助力量、一击必杀等）。
   - **记忆**（v4）加入最近三次交手：双方 HP 变化、对手新暴露的招式、对手是否换人，以及"没有可见效果"。
3. **`render.py`** 把这些整理成一个结构化 JSON 状态：`situation` 加上全部 `options`，有意图时再加上设计师意图。然后只问 **一个选择题**："选出最可能赢的选项……"；有意图时则问："哪个选项遵守 `designer_intent`？若有多个，选最有利于取胜的那个。"
4. **Jev** 返回每个选项的概率，**`decider.py`** 采用它的选择。API 出错或达到预算时回退到规则（计为一次回退）。只有一个合法选项的回合不调用 API。
5. **`player.py`** 执行指令（太晶化选项会带 `terastallize=True`），记录请求和决策；poke-env 保存回放，供查看器使用。

## 为什么这样分工

Jev（"System One"）返回的是校准过的选择，不是文本。我们的受控测试结果：

| 任务 | 结果 |
|---|---|
| 对**输入中已写明**的数字做阈值、比较、选最优和与/或/非/除非判断 | **100%** |
| 两步指代（"最近治疗过 Boss 当前目标的队员"） | 随机水平 |
| 长列表计数 | 差一 |
| 每个问题**只展示一个选项**时判断比较类意图（"最弱的击倒招式"） | 差 |
| 同样的意图，**所有选项可见** | 好 |

所以设计原则是：**计算交给代码，展示全部选项，只问一个直接的问题。** Jev 的官方文档也是这么建议的（"Jev 不是计算器"，避免多层指代，避免大量无关状态）。

## 规则基线

`rules.py` 刻意保持简单：有可能击倒的招式时，选命中率最高的击倒招式；否则选伤害 × 命中率最高的招式。只有在被迫换人，或当前对位非常差且有好的换人对象时才换人。规则用于回退，也用来界定意图的冲突回合。

## 文件

| 文件 | 作用 |
|---|---|
| `facts.py` | 所有数字，包括计算器、太晶化、对手威胁和速度 |
| `render.py` | 模型输入，以及第二阶段的后果简报（v3） |
| `decider.py` | `JevDecider`（可选 `two_stage`）与 `RuleDecider` |
| `player.py` | poke-env 玩家：历史计数、记忆、太晶化指令、回放 |
| `features.py` | 命名版本 `v01` … `v4` |
| `jev.py` | API 客户端（固定 `jev-1.13.0`、重试、成本统计）和免费的模拟客户端 |
